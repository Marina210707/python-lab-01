## Аналіз GIL (Global Interpreter Lock)
1. **Чому потоки під GIL не прискорили індексацію?**
   Індексація — це CPU-bound задача (обробка тексту, токенізація, створення словників). GIL дозволяє виконувати байт-код Python лише одному потоку в один момент часу. Тому потоки не дають реального паралелізму для CPU-задач, а лише створюють накладні витрати на перемикання контексту (тому час навіть зріс).

2. **Чому процеси прискорили і чим це оплачено?**
   Процеси мають власний інтерпретатор Python і власний GIL. Вони можуть виконуватися на різних ядрах процесора одночасно. Прискорення на 8 воркерах (0.9585 с) хоч і невелике, але є. **Ціна:** створення процесу — це дорога операція (копіювання пам'яті, серіалізація даних через `pickle` для передачі між процесами). Тому на маленьких задачах процеси можуть бути навіть повільнішими за serial (як видно на 2 воркерах — 1.5696 с).

3. **Де в часі merge видно закон Амада?**
   Закон Амада каже, що прискорення обмежене тією частиною програми, яку неможливо паралелити. У нас `merge` виконується послідовно в головному потоці. Чим більше воркерів, тим більше часу йде на `merge`, і це обмежує загальне прискорення. Саме тому на 8 процесах ми не отримали прискорення в 8 разів.

## Висновок
Для CPU-bound задач у Python (як індексація) краще використовувати `ProcessPoolExecutor`, але тільки для великих обсягів даних, щоб виправдати витрати на міжпроцесну взаємодію. Для I/O-bound задач (читання файлів) краще підходять потоки.
