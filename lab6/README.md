# Лабораторна робота 6: Асинхронний краулер

[![CI](https://github.com/Marina210707/python-lab-01/actions/workflows/ci.yml/badge.svg)](https://github.com/Marina210707/python-lab-01/actions/workflows/ci.yml)

## Опис
Реалізовано асинхронний краулер на базі `asyncio` та `aiohttp`. Краулер вміє:
- Обходити сторінки в межах одного домену.
- Обробляти помилки (таймаути, 429, 5xx).
- Використовувати семафор для обмеження кількості одночасних запитів.
- Зберігати зібрані тексти у файли.

## Дозвіл на краулінг
Для тестування використовувався **локальний сервер** (`http://localhost:8080`), який було створено спеціально для цієї лабораторної. Жодні реальні сайти не піддавалися навантаженню.

## Результати бенчмарку
Тестування проводилося на локальному сервері з 2 сторінками. Для перевірки роботи краулера на реальних обсягах можна запустити його на локальному дзеркалі.

| Concurrency | Час (сек) | Сторінок/сек |
| :--- | :--- | :--- |
| 1 | ~0.5 | ~4 |
| 5 | ~0.2 | ~10 |
| 20 | ~0.1 | ~20 |

*(Цифри приблизні, оскільки локальний сервер дуже швидкий. На реальних сайтах різниця буде більш помітною).*

## Аналіз
1. **Чому 20 одночасних запитів швидші за 1?**
   Тому що краулер не чекає, поки завершиться один запит, а надсилає наступний. Це дозволяє ефективно використовувати час очікування мережі (I/O-bound задача).

2. **Чим це коштує?**
   Ліміт на кількість з'єднань (семафор) потрібен, щоб не перевантажити сервер і не отримати бан. Також це споживає більше пам'яті та ресурсів CPU на обробку одночасних відповідей.

3. **Де цикл подій зупинився б, якби індексація йшла всередині корутини?**
   Якби ми викликали синхронну функцію індексації всередині корутини, вона б заблокувала цикл подій (event loop) на весь час своєї роботи. Краулер не міг би обробляти інші запити, поки індексація не завершиться. Тому індексацію треба виносити в окремий потік або процес.
